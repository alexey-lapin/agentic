# Conversion audit

Everything a visitor sees before deciding to press star. A checkmark helps nobody; a named fix is the deliverable.

Most of the metadata comes from one call:

```
gh repo view <owner/repo> --json description,repositoryTopics,homepageUrl,usesCustomOpenGraphImage,licenseInfo,latestRelease,hasDiscussionsEnabled,openGraphImageUrl
```

## 1. The pitch

Can a stranger say what this does and who it is for, in ten seconds, from the description and the first heading alone? Everything below is downstream of this. Score it before anything else, and where the answer is no, the pitch is the first fix in the plan.

Weak: accurate but generic, indistinguishable from twenty other repos in the same niche.
Fix: one sentence naming the thing, the stack or domain, and the one property that separates it from the alternatives.

## 2. Repo description

The line under the repo name, and the text that shows in search results and in every link preview.

Weak: restates the repo name, or describes a category rather than this repo.
Fix: the pitch from item 1, trimmed to fit. Front-load the distinguishing word.

## 3. Topics

GitHub topic search is a real discovery path.

Weak: fewer than five, or all of them generic. GitHub allows 20.
Fix: fill toward 20 with the stack, the domain, the ecosystem, the language version, and any spec or standard implemented. Check what comparable repos use and match the vocabulary people search with. A version-specific topic pair such as the language version plus the framework major is a real discovery path and usually uncrowded.

## 4. Homepage URL

Weak: empty, or pointing somewhere other than this project (a spec, an upstream org, a framework's site). That field is prime placement and pointing it away wastes it.
Fix: the live demo, the docs site, or the package page.

## 5. Social preview image

Every link shared anywhere renders as this image. The default is autogenerated and reads as an unmaintained repo.

Weak: `usesCustomOpenGraphImage` is false.
Fix: a 1280x640 image with the name, the pitch, and the stack, legible at thumbnail size.

## 6. README first screen

What a reader sees before scrolling. Without a browser, treat the first screen as the first 25 rendered lines, counting an image as roughly 10 and a badge row as 1.

Weak: badges and a wall of prose before the reader learns what the thing does or sees it working.
Fix: name, one-line pitch, a demo image or GIF, then the shortest path to running it. Everything else moves below.

## 7. Demo

An image, a GIF, a hosted instance, or a playground.

Weak: text-only, or a link to a demo that is cold-starting or dead. Check that it responds.
Fix: for a CLI or TUI, a terminal GIF. For a service, a hosted instance plus a screenshot of the API docs. For a library, the smallest snippet that shows the point, in the first screen. For a learning resource or reference implementation, the demo is the thing being taught: an architecture diagram, a guided path through the code, or a recording of the property the repo exists to demonstrate.

## 8. Time to first run

Count the steps from landing on the page to something working locally.

Weak: more than three commands, or any step requiring a decision the reader is not equipped to make.
Fix: one copy-paste block that works. A container or a script is fine. Move the full setup to a separate document.

## 9. License

Weak: missing, or present as a file GitHub does not detect (`licenseInfo` is null).
Fix: a detected SPDX license. Missing licenses stop people using the code at work, and people who cannot use it do not star it.

## 10. Badges

Weak: more than about four, or any that are red, stale, or decorative.
Fix: keep the ones carrying live signal, usually build, coverage, version, and license. Delete the rest. A row of badges reads as noise, and a failing one reads as abandoned.

## 11. Releases

Weak: no releases, or releases with autogenerated notes only.
Fix: tagged releases with notes a user can read, and attached artifacts where the project produces any.

## 12. Contributor on-ramp

Applicable only when the intake said contributors are a goal. Otherwise score `n/a` and name that condition.

Weak: no `CONTRIBUTING`, no labelled starter issues, no pinned issue explaining where to begin.
Fix: a short `CONTRIBUTING`, three or more `good first issue` items that are genuinely small, and a pinned issue naming the current direction.

## 13. Signals of life

Last commit date, open issue response times, whether Discussions is on and used.

Weak: months of silence on issues, or Discussions enabled and empty, which reads worse than off.
Fix: close or answer stale issues before any distribution push. Visitors arriving from a launch check this first, and a dead issue tracker cancels the launch.

## 14. Claims match reality

Read the README as a skeptical expert would, and check its claims against the repo.

Two failures, both common and both expensive. An unsupportable claim ("production-ready", "battle-tested", "blazing fast") that the code and the demo cannot substantiate: an experienced reader spots it, discounts everything after it, and leaves. And an instruction that does not work: a stated prerequisite version that contradicts the build files, a quickstart command that fails, a demo link that is dead. Run the quickstart, or at minimum diff every version the README states against the build configuration.

Weak: a claim the repo cannot back, or an instruction that no longer matches the build.
Fix: delete the claim and state what the repo actually demonstrates, which is usually more interesting. Correct the instruction, and note that this is a bug in the repo rather than a marketing item.
